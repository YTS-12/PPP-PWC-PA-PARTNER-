# PA Insight (가칭)

DART 공시 신호로 **회계·결산 지원(PA) · 내부회계관리제도 · IFRS 18 도입 지원 · 재무자문·구조조정** 제안 후보를 찾는 웹 프로토타입입니다.
코스피·코스닥 상장사 OpenDART 공시를 **기존 수집본(2026-10-04 기준) + 추가 수집** 방식으로 씁니다.

- 공시 데이터: `public/data/` 의 JSON. 기존 수집본에 **추가 수집 5종(주요계정·주요사항보고서·거래소공시·연장신고·2026 반기 감사인)을 모두 반영**했습니다(2026-10-05 수집). Q1 검증 뒤 **수집 2종(감사인 보완·정정공시 확인)과 거래소 시장조치 추출**을 더해 10/6에 다시 수집·빌드했고, 재검증 뒤 **감사인 화면 보완(`collect:auditor-web`)과 시장조치 규칙 조정**을 더해 다시 반영합니다(아래 3절). 데이터 기준일과 반영 상태는 대시보드 '데이터 상태'에서 봅니다.
- 배포 주소: https://ppp-rose-two.vercel.app (2026-10-30까지 유지) · 저장소: https://github.com/YTS-12/PPP-PWC-PA-PARTNER- (공개 · 2026-10-08 심사용으로 전환)

2. 이 폴더(`C:\Users\yjh51\Desktop\PPP`)에서 의존성을 설치합니다.

   ```powershell
   cd C:\Users\yjh51\Desktop\PPP
   npm install
   ```

3. 화면을 띄웁니다. → 브라우저에서 http://localhost:3000

   ```powershell

   ```

   Supabase 키가 없어도 **'로그인 없이 둘러보기'** 로 모든 화면을 쓸 수 있습니다.

## 2. `.env` 만들기

`.env.example` 을 복사해 `.env` 를 만들고, 메모장으로 열어 값을 채웁니다. (`.env` 는 깃허브에 올라가지 않습니다)

```powershell
copy .env.example .env
notepad .env
```

| 변수 | 내용 |
| --- | --- |
| `DART_API_KEY` | OpenDART 인증키(1개). 추가 수집에만 씀 |
| `DART_BASE_URL` | 모의 서버 시험 전용. `http://127.0.0.1:포트`·`http://localhost:포트` 만 받고(캐시는 `data/raw/_mock/` 에 따로), **실제 수집 때는 비워 둡니다** |
| `DARTWEB_BASE_URL` | (선택, `.env.example` 에 주석으로 있음) `collect:corrections`·`collect:auditor-web` 의 DART 공시 화면 모의 서버 시험 전용. 같은 주소 규칙이고 화면 캐시는 `data/raw/_mock/dartweb/` 에 따로 쌓입니다. **실제 수집 때는 넣지 않습니다** |

| `NEXT_PUBLIC_SUPABASE_URL` · `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase 프로젝트 URL과 anon(publishable) 키 |
| `CRON_SECRET` | Vercel 크론 확인용 임의 값 (영문·숫자 20자 이상 아무 문자열) |

`.env` 를 바꾼 뒤에는 `npm run dev` 를 껐다 켜야 반영됩니다. Vercel 환경변수도 바꾼 뒤 다시 배포해야 반영됩니다.

## 3. 추가 수집 → 데이터 다시 만들기

기존 수집본에 없는 데이터만 더 받습니다. 대상은 `data/universe.json` 의 2,555곳(스팩·리츠·펀드 제외)입니다.
이 PC 한 대에서 여덟 가지를 모두 받습니다(OpenDART 키 1개. 2026-10-05 변경, 10/6 Q1 검증 뒤 6·8번, 재검증 뒤 7번 추가).
OpenDART 는 키 1개당 하루 20,000건 한도이며, 1~6번을 모두 합쳐 약 3,600\~5,400건(한도의 18\~27%, 추정)입니다.
7번(`collect:auditor-web`)과 8번(`collect:corrections`)은 OpenDART 가 아니라 **DART 공시 화면**(dart.fss.or.kr)을 1초에 1건씩 읽습니다(7번 약 110\~260건·약 2\~5분, 8번 약 650\~700건·약 12\~15분, 추정. OpenDART 한도와 별개).
받은 원본은 `data/raw/` 에 캐시돼서, 중간에 끊겨도 **같은 명령을 다시 실행하면 이어서** 받습니다.

아래 순서대로, 기본은 옵션 없이 실행합니다: **fin → major → krx → deadline → auditor → auditor-supp → auditor-web → corrections → `data:build`**.
6번은 5번 결과를, 7번은 5·6번 결과를, 8번은 2·3·4번 결과를 대상으로 쓰므로 그 뒤에 돌립니다. 5·6번을 다시 받으면 7번을, 2·3·4번을 다시 받으면 8번을 다시 실행합니다(받은 화면은 캐시라 새로 필요한 화면만 요청).

| 순서 | 명령 | 받는 것 | 호출 수(예상) | 풀리는 신호 |
| --- | --- | --- | --- | --- |
| 1 | `npm run collect:fin` | 주요계정 재수집 (연결·별도 전체 계정). 자본금 행이 없는 곳만 단일회사 전체 재무제표로 보완 | 약 30 + 자본금 보완 약 30 | IF1 영업외손익, RS3 자본잠식, IC1 정확화 |
| 2 | `npm run collect:major` | 주요사항보고서 12개월 | 10~60 | RS1 부도·회생·채권은행 관리(개시·중단)(감자·영업정지는 조건부), PA3·IC3에 분할·영업양도 추가 |
| 3 | `npm run collect:krx` | 거래소공시 12개월 (횡령·배임 + 거래소 시장조치: 실질심사·상장폐지 사유·관리종목·반기 부적정·내부결산 기준(감사 전)·중요한 영업정지). 시장조치는 같은 응답에서 고르므로 새 호출 없음. 중요한 영업정지 거래정지는 근거 공시 목록에만 남고 신호 근거는 아님 | 수백~1,200 | IC2 횡령·배임, RS1 거래소 시장조치 |
| 4 | `npm run collect:deadline` | 제출기한 연장신고 (2024\~2026년 3/1\~4/10, 공시유형 전체) | 수백\~1,200 | PA1 연장신고 |
| 5 | `npm run collect:auditor` | 2026 반기 감사인 (2,555곳 한 번에) | 약 2,560 | 현재 감사인(독립성), PA2 확정 |
| 6 | `npm run collect:auditor-supp` | 감사인 보완: OpenDART '감사용역체결현황'(`adtServcCnclsSttus`)의 당기 감사인. 2026 반기 감사인을 못 얻은 곳('-'·감사인 아님·당반기 행 없음·반기보고서 없음)은 2026 반기, 기존 수집본에 2025 감사인이 없는 곳은 2025 사업보고서(`DATA_DIR` 없으면 2026만) | 약 210 (10/5 기준 143 + 71) | 현재 감사인(독립성), PA2 |
| 7 | `npm run collect:auditor-web` | 감사인 화면 보완: 5·6번 두 API로 감사인을 얻지 못한 보고서(2026 반기 약 54곳, 2025 사업보고서 감사인이 없는 곳)의 DART 공시 화면 '외부감사에 관한 사항' 표에서 당기·당반기 감사인 (보고서 1건에 화면 2번) | DART 화면 약 110\~260 (약 54\~130곳) · OpenDART 0 | 현재 감사인(독립성), PA2 |
| 8 | `npm run collect:corrections` | 정정공시 확인: 2·3·4번 결과 중 [기재정정]·[첨부정정]·[첨부추가] 등 정정류 공시의 최초 공시일·원공시 접수번호·철회·취하 여부·거래소 시장조치 사유 해소 여부·첨부정정 여부 (DART 공시 화면, 공시 1건에 화면 2번. 첨부정정은 같은 원공시의 다른 정정 버전도 확인) | DART 화면 약 650\~700 (대상 약 330건) · OpenDART 0 | PA3·IC3·RS1·IC2·PA1 근거일(최초 공시일 기준 12개월)·철회·사유 해소 제외·원공시 링크 |

- **2·3번(major·krx)은 같은 날 끝냅니다.** 조회 종료일이 실행일이라, 다음 날 옵션 없이 다시 돌리면 구간이 바뀌어 캐시를 못 쓰고 처음부터 다시 호출합니다. 시작할 때 `조회 종료일 YYYYMMDD` 를 `====` 줄 사이에 크게 보여 주고, 실패·중단하면 `다시 실행: npm run collect:major -- --end YYYYMMDD` 를 함께 출력합니다. 다음 날 이어받을 때도 그 명령(같은 `--end`)을 그대로 씁니다. 예) `npm run collect:major -- --end 20261005`
- 5번(auditor)이 가장 오래 걸립니다(약 10~25분). 8번(corrections)도 1초 간격이라 약 12~15분, 7번(auditor-web)은 약 2~5분 걸립니다. 그동안 Supabase·배포 작업을 해도 됩니다.
- 10/5 수집분과 같은 구간으로 다시 돌릴 때(Q1 뒤 재수집)는 `npm run collect:krx -- --end 20261005` 처럼 첫 실행일을 주면 캐시만 읽어 새 호출 없이 시장조치를 다시 뽑습니다. 구간을 오늘로 옮기려면 2·3번을 같은 날 함께 다시 받습니다.

**저장하지 않고 멈추는 경우** — 아래 경우에는 `중단: …` 을 출력하고 결과 파일(`data/extra/` 의 `*.jsonl`·`*.meta.json`)을 쓰지 않습니다. 받은 응답은 `data/raw/` 캐시에 남아 있어, 원인을 확인하고 같은 명령을 다시 실행하면 새 호출이 거의 없습니다.

- 응답 상태가 정상(000·013)이 아닌 요청이 하나라도 있을 때(OpenDART 명령 모두). `[이름] 확인 필요 N건` 과 상위 10건(상태코드·메시지·요청 인자)을 보여 주고, 다시 실행하면 그 요청만 다시 받습니다. major·krx·deadline 은 도중에 `경고: … 결과는 저장 전 중단됨` 이 먼저 보입니다.
- `collect:fin` — 주요계정을 받은 회사가 대상의 90% 미만일 때. 원인을 확인한 뒤에만 `-- --allow-low` 를 붙여 저장합니다.
- `collect:deadline` — 연장신고가 0건일 때. 함께 출력되는 '연장' 제목 목록으로 제목 규칙을 확인하고, 정말 0건이면 `-- --allow-empty` 를 붙여 저장합니다.
- `collect:corrections` — DART 공시 화면을 받지 못했거나(HTTP 오류·이상 화면) 공시 화면에서 버전 목록을 읽지 못한 공시가 1건이라도 있을 때(화면 형식이 바뀐 것으로 봄). 403·429(차단·과다 요청)는 그 자리에서 멈춥니다. 받은 화면은 `data/raw/dartweb/` 에 캐시돼, 다시 실행하면 받은 화면은 새로 요청하지 않습니다.
- `collect:auditor-web` — DART 공시 화면을 받지 못했거나 공시 화면에서 목차를 읽지 못한 보고서가 1건이라도 있을 때. 403·429 는 그 자리에서 멈춥니다. 목차에 '외부감사에 관한 사항'이 없는 보고서는 멈추지 않고 '외부감사 항목 없음'으로 저장·출력합니다. 화면 캐시는 8번과 같은 `data/raw/dartweb/` 입니다.
- 하루 한도(020)·인증키 문제·같은 요청 4번 실패(2·4·8초 뒤 다시 시도)·정상 응답 없이 비정상 응답 10번 연속은 그 자리에서 멈춥니다. 다음 날(020) 또는 원인을 고친 뒤 같은 명령으로 이어받습니다.
- 수집 플래그(`--part`·`--year`·`--fallback`·`--end`·`--years`·`--type`) 뒤에 값을 빠뜨리면 기본값으로 넘어가지 않고 호출 전에 멈춥니다.

각 단계에서 볼 출력입니다. 모든 명령은 `[이름] 새 호출 N건 · 캐시 N건 · 정상 N · 데이터 없음 N · 기타 N · 확인 필요 N건` 을 출력하고, 저장했을 때만 `완료: …` 를 출력합니다.

1. `collect:fin` — 받은 회사 `N/2555곳` 과 매칭 안 된 계정명, `자본금 보완: 주요계정에 자본금이 없는 N건(N곳)…`. 계정명 앞 번호 머리('(1)자본금'·'1.자본금'·'Ⅰ.자본금' 등)는 지운 뒤 매칭합니다. 자본금·세전이익 변형이 보이면 `scripts/collect/fin.mjs` 계정 규칙에 추가합니다. 90% 미만이면 위처럼 저장하지 않고 멈춥니다. 출시 합격 기준은 95% 이상이라, 90\~95%면 저장은 되지만 계정 규칙을 보완해 다시 실행합니다.
2. `collect:major` — 맨 위 조회 종료일, 구간·시장별 건수, `완료: 대상 기업 주요사항보고서 N건 … (조회 종료일 YYYYMMDD)`.
3. `collect:krx` — 맨 위 조회 종료일, 구간·시장별 건수, `거래소공시 N건 중 대상 기업 N건: 횡령·배임 N건 · 시장조치 N건`, `시장조치 유형별: …`, `제목 예(횡령·배임):` 최대 10개와 시장조치 종류별 제목 예, `시장조치 규칙 밖 제목` 목록(우려·해제·관련 안내 등, 많은 순 10개), `완료: …`. 횡령·배임 표기가 잡히는지, 규칙 밖 목록에 넣어야 할 시장조치가 없는지 봅니다.
4. `collect:deadline` — 연도·시장별 `N건 확인`, `제목 규칙에 맞는 대상 기업 연장신고: N건`, `완료: 연장신고 N건`. 공시검색 응답에는 공시유형 필드가 없어 유형으로 좁힐 수 없으니, 옵션 없이 유형 전체·3개년으로 받습니다. `npm run collect:deadline -- --probe` 는 '연장'이 들어간 실제 제목 목록(규칙에 안 맞는 제목은 `← 규칙 밖`)만 보여 주고 **파일은 쓰지 않습니다**. 이미 받은 응답은 캐시라 새 호출이 거의 없습니다. 기간이 3/1~4/10 이라 12월 결산이 아닌 회사(대상 중 31곳)는 판정 범위 밖이고, 상세 화면에 그 이유가 나옵니다.
   - 기간은 연도·시장마다 `3/1~3/19` 와 `3/20~4/10` 두 구간으로 나눠 조회합니다. 10/5 첫 수집은 3/20~4/10 만 받아 3/20 전에 낸 연장신고(예: 2026-03-16·03-18 접수)를 놓쳤습니다. 다시 실행하면 3/20~4/10 은 캐시를 쓰고 3/1~3/19 만 새로 받으니, `npm run collect:deadline` → `npm run data:build` 순서로 다시 돌려 반영합니다.
5. `collect:auditor` — 200곳마다 진행 상황, 끝에 `감사인 확인 N곳`.
6. `collect:auditor-supp` — 맨 위 `2026 반기 N곳 · 2025 사업보고서 N곳 = 요청 N건`, 100건마다 진행 상황, 끝에 `감사인 찾음: 2026 반기 N/M곳 · 2025 N/M곳 · 데이터 없음(013) N건` 과 감사인 아님으로 버린 값 상위 10개, `완료: 감사인 보완 N건(찾음 N건)`. 여기서 못 찾은 회사는 7번이 DART 공시 화면에서 다시 찾습니다.
7. `collect:auditor-web` — 맨 위 `감사인 보완(DART 공시 화면): 2026 반기 N곳 · 2025 사업보고서 N곳 = 화면 약 N번, 1초 간격`(접수번호가 없어 건너뛴 곳 수 포함), 20곳마다 진행 상황, 끝에 `감사인 찾음: 2026 반기 N/M곳 · 2025 N/M곳`, 감사인 아님으로 버린 값 상위 10개, 첫 표에서 못 얻어 '감사용역 체결현황' 표로 찾은 곳·목차에서 외부감사 항목을 못 찾은 곳·'사업연도·감사인' 표를 못 찾은 곳·반기보고서·사업보고서가 아닌 화면(접수번호 확인 필요)을 각각 최대 10개, `완료: 감사인 보완(DART 공시 화면) N건(찾음 N건)`. 그래도 못 찾은 회사는 화면에 '감사인 미확인'으로 남습니다. 원문으로 확인한 기대값: 한화오션 2026 한영회계법인(지정감사), 아시아나항공 2025·2026 삼정회계법인, 케이뱅크 2025 안진회계법인·2026 삼일회계법인, 에이아이코리아 2026 삼일회계법인.
8. `collect:corrections` — 맨 위 대상 건수, 25건마다 진행 상황, 끝에 `최초 공시일 확인 N/M건 · 원공시 접수번호 N건 · 첨부정정류 N건 · 철회·취하 등 N건`, 철회 감지 목록(최대 40건, 키워드와 정정사유. 거래소 시장조치의 '사유 해소'와 형제 기재정정에서 찾은 철회 포함), 정정신고 부분을 못 읽은 공시(원공시 정보만 저장), `완료: 정정공시 N건(철회·취하 등 N건)`. 철회·사유 해소 감지는 키워드 방식이라 목록을 한 번 훑어봅니다.

수집 결과는 대시보드 '데이터 상태'에 `반영 · 수집 YYYY-MM-DD · 개수` 로 보입니다(`npm run data:build` 뒤, 칩 8개). 개수는 주요계정이 받은 회사 `N곳`, 감사인이 `감사인 확인 N곳`, 주요사항·거래소공시·연장신고·감사인 보완·감사인 화면 보완·정정공시 확인이 `N건` 입니다. 0이거나 감사인 파트가 덜 모이면 주황색입니다.

### 여럿이 나눠 받을 때 (선택)

키가 여러 개라 나눠 받고 싶을 때만 씁니다. 감사인은 `npm run collect:auditor -- --part 1/2`, `-- --part 2/2` 로 나눌 수 있고, 결과는 `data/extra/` 에 명령·파트마다 다른 파일로 생겨 충돌하지 않습니다. 다른 사람은 결과 파일만 전달하고, `data:build`·커밋·푸시는 저장소 주인 한 사람만 합니다(Vercel Hobby는 비공개 저장소에서 다른 사람의 커밋을 배포하지 않음).

수집이 끝나면 화면용 데이터를 다시 만듭니다. (`.env` 에 `DATA_DIR` 를 채운 PC에서)

```powershell
npm run data:build
```

신호별 해당 기업 수가 출력됩니다. 추가 수집 전인 신호는 화면에서 '추가 수집 전'으로 비활성 표시됩니다. 만든 뒤 `data/extra/` 와 `public/data/` 를 함께 커밋·푸시하면 Vercel이 다시 배포합니다.

### 화면에 보이는 표시 (10/5 점검·10/6 Q1 검증·재검증 뒤 바뀐 것)

자세한 규칙은 `docs/design.md` 에 있고, 문구는 모두 `config/signals.json` 에서 고칩니다(화면·스크립트에 문구를 따로 쓰지 않음).

- **정정공시 날짜**: 공시검색은 최종 보고서만 받아 근거가 정정공시일 수 있습니다. 8번(`collect:corrections`)으로 최초 공시일을 알면 근거 날짜가 '최초 YYYY-MM-DD · 정정 YYYY-MM-DD' 로 나오고, **최근 12개월은 최초 공시일 기준**으로 봅니다. 최초일을 모르면(8번 전 등) 근거 문구 끝에 '(정정공시)', 목록에 '정정' 태그가 붙고 정정 접수일 기준입니다.
- **첨부정정**: [첨부정정]·[첨부추가]처럼 첨부서류만 고친 정정은 DART 원문 링크가 결정 본문이 있는 원공시로 갑니다('첨부정정 · 원공시로 연결').
- **신호 제외** 태그(근거 공시 목록): 정정 내용이 철회·취하·부결 등이면 '신호 제외 · 철회·취하 확인'([첨부정정]은 같은 원공시의 다른 정정 버전에 적힌 철회도 봄), 거래소 시장조치·내부결산 공시의 정정에 '해당 사유가 해소되었습니다' 같은 문구가 있으면 '신호 제외 · 사유 해소 확인', 정정본만 12개월 안이고 최초 공시가 그 전이면 '신호 제외 · 최초 공시 12개월 전', 영업정지 공시에 따라 그날 자동으로 걸린 '주권매매거래정지(중요한 영업정지)'는 '신호 제외 · 영업정지 공시에 따른 자동 정지'. 감자결정은 자본잠식 50% 이상(RS3)일 때만, 영업정지는 감사의견 비적정(RS2)·자본잠식 50% 이상(RS3)이 있거나 최근 12개월 거래소 시장조치(자동 정지 제외)가 있을 때만 RS1 신호이고, 아니면 '신호 제외 · 자본잠식 50% 미만' / '신호 제외 · 자본잠식 확인 불가' / '신호 제외 · 재무위험 신호 없음'. 감자 안내는 목적을 단정하지 않고 '감자 사유(결손보전·주주환원 등)는 원문에서 확인해 주세요' 로 씁니다.
- **RS1** 이름이 '부도·회생·채권은행 관리·거래소 조치 공시 (감자·영업정지는 조건부)' 로 바뀌었습니다. 거래소 시장조치(상장폐지 사유·실질심사·반기 부적정·관리종목 지정·내부결산 기준 사유 발생(감사 전))와 채권은행 관리절차 중단도 근거이고, 시장조치 근거 앞에 '[거래소]' 가 붙습니다. 영업정지 공시에 따라 그날 자동으로 걸리는 '주권매매거래정지(중요한 영업정지)'는 거래소의 별도 확인이 아니라 근거에서 빼고, 영업정지 예외에도 쓰지 않습니다. 대표 근거는 부도 > 회생 > 해산 > 채권은행 관리 > 거래소 시장조치 > 감자 > 영업정지 순(시장조치끼리는 상장폐지 사유 > 실질심사 > 반기 부적정 등 > 관리종목 > 내부결산 기준), 회사당 1점입니다.
- **IC2** 이름이 '횡령·배임 관련 공시' 로 바뀌고 근거 앞에 유형([혐의발생]·[진행사항 · 결과 확인 필요]·[사실확인 · 결과 확인 필요]·[관련 공시 · 사실 확인 전])이 붙습니다. 자회사 공시는 '자회사' 로 표시하고, 같은 날이면 자사 공시가 대표 근거입니다.
- **PA3·IC3**: 영업양도결정도 근거입니다('합병·분할·영업양수도 결정').
- **RS3**: 2025 사업보고서가 없어 2024 값으로 판정하면 '(2025 사업보고서 미제출 · 이후 감자·분기보고서로 달라졌을 수 있어요)' 가 붙습니다.
- **감사인**: 현재 감사인은 2026 반기 → 감사용역체결현황(6번) → DART 공시 화면(7번) → 2025 사업보고서 → 감사용역체결현황 → DART 공시 화면 순으로 공시에서 확인한 값만 씁니다(출처에 '(감사용역 체결현황)'·'(DART 공시 화면)' 표시). 끝내 못 찾으면 주황 '감사인 미확인' 이고, 이력상 최근 감사인은 '감사인 미확인 · ○○(추정)' 으로 **표시만 하고 숨기지 않습니다**(이력상 삼일이면 주황 경고 '이력상 최근 감사인 삼일 · 현재 감사인 확인 필요'). 이력으로 숨기면 감사인을 바꾼 회사가 잘못 숨겨지기 때문입니다(Q1: 아시아나항공은 이력상 삼일이지만 실제 삼정). 이력도 없으면 '감사인 미확인 · 독립성 확인 필요'.
- PA2 근거 문구 앞에 유형 머리말([2027 도래 가능]·[지정 유예·이월 확인]·[2026 지정 첫해 추정]·[2026 감사인 확인 필요])이 붙습니다.
- 점수: IC1과 IF3는 같은 '자산 규모' 사실이라 합쳐 1점으로 셉니다(PA3·IC3처럼).
- 대시보드 '최근 3개월 신호 공시'는 삼일 감사 고객을 숨기면 그 회사 공시를 빼고 셉니다.
- 상세 화면 맨 아래에 '판정하지 않은 이유'(재무 없음·12월 결산 아님·자본금 없음·감사의견 없음 등)가 나옵니다. 전액잠식 회사의 부채비율은 '자본잠식'으로 보입니다.
- 추천 목록 CSV 끝에 데이터 기준일과 면책 문구 두 줄이 붙습니다. 내 후보 화면에서도 지금 보이는 상태 탭의 후보를 CSV로 내보낼 수 있습니다.

## 4. Supabase 설정 (로그인·개인 맞춤)

Vercel 첫 배포 전에 끝내 URL과 anon 키를 확보해 둡니다.

1. https://supabase.com 에서 무료 프로젝트를 만듭니다. (리전은 가능하면 Seoul)
2. **SQL Editor** 에 `supabase/migrations/001_user_tables.sql` 내용을 붙여 넣고 Run.
3. **Authentication → Sign In / Providers → Email**: 사용 켜기, **Confirm email 끄기**, 최소 비밀번호 8자.
4. **Authentication → Rate Limits**: 로그인·가입 한도를 넉넉히 올립니다. (사내에서 같은 IP로 몰릴 수 있음)
5. **Project Settings → API** 에서 URL과 anon(publishable) 키를 `.env` 에 넣고 `npm run dev` 재시작.

## 5. 깃허브 → Vercel 배포 (Claude Code)

추가 수집을 기다리지 않고 기존 수집본 데이터로 먼저 배포한 뒤, 추가 수집분을 푸시해 다시 배포합니다. 2026-10-05에 아래 순서로 배포를 마쳤습니다(배포 주소 https://ppp-rose-two.vercel.app, 저장소 `YTS-12/PPP-PWC-PA-PARTNER-` 의 `main`). 지금은 고친 뒤 커밋·푸시하면 Vercel이 자동으로 다시 배포합니다.

1. 깃허브 웹에서 개인 계정에 **비공개 저장소**를 만듭니다. README·.gitignore·license는 모두 체크하지 않은 빈 저장소로 만들고, 기본 브랜치는 `main` 입니다.
   팀원은 초대하지 않습니다. (Vercel Hobby는 비공개 저장소 협업을 지원하지 않음)
2. 커밋 작성자 이메일을 그 깃허브 계정에 **인증된 이메일**로 설정합니다. 커밋 작성자가 Vercel에 연결한 깃허브 계정 본인이어야 배포됩니다.

   ```powershell
   git config user.name "<깃허브 사용자명>"
   git config user.email "<깃허브 계정에 인증된 이메일>"
   ```

3. Claude Code로 이 폴더를 그 저장소의 `main` 에 올립니다. `.env` 와 `data/raw/` 는 올라가지 않습니다.
   `public/data/` 와 `data/universe.json` 은 반드시 함께 올립니다. (Vercel에는 기존 수집본 폴더가 없음)
4. Vercel에서 저장소를 Import → Import 화면의 Environment Variables에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `CRON_SECRET` 3개를 넣고 첫 Deploy.
   **`DART_API_KEY` 는 Vercel에 넣지 않습니다.** 환경변수는 `NEXT_PUBLIC_` 값을 포함해 모두, 바꾼 뒤 다시 배포(Redeploy)해야 반영됩니다.
5. Supabase → Authentication → URL Configuration의 Site URL을 Vercel 주소로 바꿉니다.
6. 배포 주소에서 5개 화면·로그인·저장을 확인하고, keepalive가 동작하는지 봅니다. Vercel → Settings → Cron Jobs 에서 Run을 누르거나, 아래처럼 헤더를 붙여 불러 본문에 `"ok":true` 가 있으면 됩니다.

   ```powershell
   curl.exe -H "Authorization: Bearer <CRON_SECRET 값>" https://<배포 주소>/api/keepalive
   ```

   브라우저로 그냥 열면 401이 정상입니다. 503은 Vercel에 Supabase 환경변수나 `CRON_SECRET`이 없음, 502는 Supabase 응답 실패(일시정지 등)입니다.
7. 추가 수집이 끝나면 `npm run data:build` → `data/extra/`·`public/data/` 커밋·푸시로 다시 배포합니다.

배포 설정은 저장소에 들어 있습니다.

- `vercel.json`: 하루 한 번(UTC 0시 = 한국 오전 9시) `/api/keepalive` 를 부르는 크론으로 Supabase 일시정지(7일 비활동)를 막고, `regions: ["icn1"]` 로 함수를 서울 리전에서 돌립니다.
- `package.json`: `engines.node` 가 `24.x` 라 Vercel도 Node.js 24로 빌드합니다.

## 자주 막히는 곳

- `DART_API_KEY가 비어 있어요` → `.env` 에 키를 넣었는지, 파일 이름이 `.env.txt` 가 아닌지 확인하세요.
- `020` (하루 한도) → 다음 날 같은 명령을 다시 실행하면 이어서 받습니다. `collect:major`·`collect:krx` 는 `-- --end <첫 실행일>` 을 붙여야 캐시를 씁니다.
- `확인 필요 N건` 또는 `오류(상태 …)가 10번 연속` 으로 멈춤 → 정상(000·013)이 아닌 응답을 받은 요청이 있다는 뜻입니다. 같은 요청이 다시 실행해도 계속 비정상 응답이면, 출력된 상위 10건(10번 연속으로 멈췄으면 마지막 응답)의 상태코드·메시지·요청 인자를 보고 키와 조회 기간(`--end`·`--year` 등) 설정을 확인하세요. 결과 파일은 쓰지 않았으니 고친 뒤 같은 명령을 다시 실행하면 됩니다.
- `collect:corrections`·`collect:auditor-web` 이 403·429 로 멈춤 → DART 공시 화면이 요청을 막은 것입니다. 한동안 기다렸다가 같은 명령을 다시 실행하면 받은 화면은 캐시로 건너뛰고 이어서 받습니다. `버전 목록(본문 선택)을 읽지 못한 공시가 N건` 으로 멈추면 DART 화면 형식이 바뀌었을 수 있으니 `data/raw/dartweb/main/` 의 해당 화면을 확인합니다.
- `2026 반기 감사인 … 이 없어요` (auditor-supp) → 5번 `npm run collect:auditor` 를 먼저 실행합니다. 7번 `collect:auditor-web` 은 5·6번 결과를 대상으로 쓰므로 5·6번 뒤에 실행합니다.
- `… 뒤에 값을 넣어 주세요` 로 멈춤 → `--part`·`--end` 같은 수집 플래그 뒤에 값을 빠뜨린 것입니다. 예) `npm run collect:major -- --end 20261005`. npm 으로 실행할 때는 플래그 앞에 `--` 를 한 번 넣어야 합니다.
- 로그인 버튼이 비활성 → `.env` 의 Supabase 값 확인 후 `npm run dev` 재시작. 배포 주소에서 그렇다면 Vercel 환경변수 확인 후 다시 배포.
- 'Confirm email이 켜져 있어요' → Supabase에서 이메일 인증을 끄세요.
- 비밀번호를 잊었거나 다른 사람이 내 이메일로 먼저 계정을 만들었음 → 비밀번호 찾기 화면은 없습니다. 담당자가 Supabase → Authentication → Users 에서 그 이메일을 삭제하면, 같은 이메일로 다시 로그인해 새 공간을 만들 수 있습니다. 이때 저장한 후보·메모·조건·프로필은 사라집니다(삭제 전에 알려 주세요).
